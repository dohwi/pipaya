# Korean and English (i18n)

pipaya ships in Korean and English, and every piece of text a person reads has to exist in both: the app, the server's
notifications, and every extension in the marketplace. This page is the rule book. A change that adds text without its
other language is not finished.

한국어 요약은 [맨 아래](#한국어-요약)에 있습니다.

## Who writes which language

| Text | Source language | The other language lives in | Checked by |
|---|---|---|---|
| App UI (`client/src`) | Korean, as the key: `t("설정")` | `client/src/lib/locales/en.ts` | `client/tests/i18n.test.ts` |
| Server notifications (push, OS) | both, side by side | `server/src/notification-text.ts` | `server/test/notification-text.test.ts` |
| Server extension (`package.json` → `pipaya`) | either | `descriptions`, `translations` | `scripts/check.ts` in pipaya-extensions |
| Client extension (`manifest`) | either | `descriptions`, `translations` | same |
| What an extension writes at run time (a status line) | both, side by side | the value itself: `{ "ko": "…", "en": "…" }` | the extension's tests |
| Agent-facing text (tool results, errors to the model, `/command` templates) | English | none: the model reads it, not a person | — |

Language tags are lowercase BCP 47 (`ko`, `en`, `pt-br`). The app picks the language in Settings → General → Language
(or the system's), and other languages come as language packs.

## The app

- **Korean is the source and the key.** Write `t("저장")` where the text is shown; add `"저장": "Save"` to `en.ts`.
- **A Korean string kept in data** (a table, a constant) is wrapped in `msg("…")` and translated where it is shown:
  `{t(row.label)}`. Never `t()` it at module load: the language can change while the app runs.
- **Parameters, never concatenation**: `t("서버 {n}개", { n })`, plural `"{n} server{n#|s}"` in English. Two halves
  glued with `+` cannot be reordered by a translation.
- **One meaning per key.** A word that means two things gets a context: `tc("optional", "선택")` and `"선택\u0004optional"`.
- **Errors meant for a person** are `LocalizedError(t("…"))`; a raw server or browser message is shown as a detail,
  not as the sentence.
- **Keep Korean on purpose** only with a reason on the same line: `// i18n-ok: <why>` (a language named in itself,
  search words typed in either language).
- Run `node client/scripts/extract-i18n.cjs`: it lists keys missing from `en.ts`, unused ones, and Korean that does not
  go through `t()`/`tc()`/`msg()`. The client tests fail on any of the three.

## Extensions

An extension's text is not in the app's dictionaries, so the extension carries its own. The same three fields work for
a server extension (`package.json` → `pipaya`) and a client extension (`manifest`).

```jsonc
{
  "description": "Blocks destructive shell commands before they run.",   // the plain one, used when nothing matches
  "pipaya": {
    "title": "Guard",
    "descriptions": { "en": "Blocks destructive shell commands…", "ko": "위험한 셸 명령을 실행 전에 막습니다…" },
    "translations": {
      "ko": {
        "Guard": "가드",
        "Block wiping disks and home": "디스크·홈 삭제 차단",
        "Stops rm -rf / and rm -rf ~.": "rm -rf /, rm -rf ~ 를 막습니다."
      }
    },
    "settings": [
      { "key": "wipe", "type": "boolean", "label": "Block wiping disks and home", "description": "Stops rm -rf / and rm -rf ~.", "default": true }
    ]
  }
}
```

- **Write the form in one language** (`label`, `description`, `placeholder`, option `label`, `title`/`name`), and put
  the other in `translations.<tag>`, keyed by the text exactly as written. English as the source is the usual choice for
  a public extension; Korean works the same way.
- **`descriptions`** holds the whole description per language; `description` is the fallback.
- **Lookup** for a reader in language L: `translations[L]`, then its base language (`pt-br` → `pt`), then English for
  a language other than Korean or English, then the text as written. A Korean reader never gets English by accident.
- **Keys and values are never translated**: `key`, option `value`, `default` and what is saved stay the same in every
  language, so a saved setting survives a language switch.
- **Status lines an extension writes** (a `readonly` field) are an object, one entry per language:
  `pi.settings.set({ ...s, statusText: { ko: "● 연결됨", en: "● Connected" } })`. The form shows the one for the
  reader (same lookup); a plain string is shown as is.
- **Notifications** an extension sends (`pi.notify`, `sdk.notify`) reach a phone while the app is closed and cannot be
  translated on the way: keep them short and write them in English unless the extension knows its reader.
- **Text for the agent** (tool descriptions, tool results, errors returned to the model, command templates) is English
  and is not translated.
- Limits: 10 languages, 300 entries each, 2000 characters per text. A bad entry is dropped by the server and refused
  by the client's manifest check.

The `pipaya-extensions` check (`bun scripts/check.ts`) fails when a form, title or description has no counterpart in
the other of Korean and English, and when a `translations` key matches nothing the extension shows.

## Reviewing a change

1. New text in the app: `t()` at the call, an `en.ts` entry, client tests green.
2. New or changed text in an extension: both languages present, `bun scripts/check.ts` green.
3. Screens: look at the change once in each language (Settings → General → Language).

## 한국어 요약

- 앱: 한국어 원문이 키입니다. 보이는 곳에서 `t("…")`, 데이터에 둘 때는 `msg("…")`, 영어는 `client/src/lib/locales/en.ts`.
  문장을 `+`로 붙이지 말고 `{n}` 매개변수를 씁니다. 일부러 남기는 한국어는 같은 줄에 `// i18n-ok: 이유`.
  `node client/scripts/extract-i18n.cjs`와 클라이언트 테스트가 빠진 번역과 `t()` 밖 한국어를 잡습니다.
- 확장: 폼·제목·설명을 한 언어로 쓰고 다른 언어는 `translations.<언어>`에 "원문 그대로 → 번역"으로 넣습니다.
  설명 전체는 `descriptions`. 한국어 사용자는 영어로 대체되지 않고, 없으면 원문이 그대로 보입니다.
  저장되는 값(`key`, 선택지 `value`)은 번역하지 않습니다.
- 확장이 쓰는 상태 문구(`readonly` 칸)는 `{ ko: "…", en: "…" }`로 둘 다 넣습니다.
- 에이전트가 읽는 문구(도구 설명·결과, 명령 템플릿)는 영어로 쓰고 번역하지 않습니다.
- `pipaya-extensions`의 `bun scripts/check.ts`가 한영 중 하나가 빠진 확장을 막습니다.
